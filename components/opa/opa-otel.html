OPA → OTEL Violation Export Link

Enables Gatekeeper disk-based violation export with an OTEL collector sidecar on the audit pod.

What This Link Does

When you link OPA to OTEL, Stacktic automatically:

  • Enables Gatekeeper's exportBackend: "disk" in helm values
  • Sets enableViolationExport: true to activate the export system
  • Configures audit connection (audit-connection) and channel (audit-channel)
  • Replaces the default fake-reader sidecar with an OTEL collector sidecar (otel/opentelemetry-collector-contrib:0.98.0)
  • Generates a ConfigMap with the OTEL collector config (filelog receiver + processors)
  • Generates a kustomize patch to mount the config into the audit pod

Data Flow Architecture

Gatekeeper Audit (every 60s scan)
   ↓ writes JSON violation records
/tmp/violations/topics/audit-channel/*.txt
   ↓ filelog receiver tails files
OTEL Collector Sidecar (same pod)
   ↓ resource + cleanup processors
OpenSearch (if opa-opensearch linked) or OTEL Collector (fallback)

Two Links Required for OpenSearch Export

The violation export pipeline requires two links working together:

Link Purpose
opa-otel Enables disk export on Gatekeeper + deploys the OTEL sidecar container
opa-opensearch Tells the sidecar WHERE to send data (OpenSearch endpoint + credentials). Also tells OpenSearch to set up index templates, dashboards, and alerting for OPA violations.

Without opa-opensearch: The sidecar falls back to sending data via OTLP to the main OTEL collector at {otel-name}-collector-collector.{otel-ns}.svc:4317

Why a Sidecar (Not Native OTEL Export)

Gatekeeper has two separate export systems:

  • metricsBackends — Aggregate metrics (constraint count, violation count). Supports OTEL natively.
  • exportBackend — Individual violation records (which pod, which constraint, what message). Only supports "disk" or "dapr". No native OTEL support.

Since we need individual violation details (not just counts), we use the disk backend + an OTEL collector sidecar to tail the violation files and export them.

Sidecar OTEL Collector Pipeline

Receiver: filelog

include: /tmp/violations/topics/**/*.txt
start_at: beginning
operators:
  - type: json_parser
    timestamp:
      parse_from: attributes.id
      layout: "%Y-%m-%dT%H:%M:%SZ"

Processor: resource

attributes:
  - key: source, value: gatekeeper, action: insert
  - key: stacktic_system, value: {system_name}, action: insert
  - key: stacktic_collector, value: opa, action: insert

Processor: attributes/cleanup

# Removes fields that cause OpenSearch mapping conflicts
actions:
  - key: resourceLabels, action: delete      # Dynamic k8s labels (nested objects)
  - key: details, action: delete              # Nested violation details
  - key: constraint_annotations, action: delete
  - key: constraint_enforcement_actions, action: delete

Exporter (depends on opa-opensearch link)

# With opa-opensearch link:
opensearch:
  http:
    endpoint: https://{opensearch-host}:{port}
    tls: { insecure_skip_verify: true }
    auth: { authenticator: basicauth/opensearch }
  logs_index: opa

# Without opa-opensearch (fallback):
otlp:
  endpoint: {otel-name}-collector-collector.{otel-ns}.svc:4317
  tls: { insecure: true }

Service

Metrics on port 9999 (avoids conflict with Gatekeeper manager on :8888). Pipeline: filelog → resource + attributes/cleanup → opensearch/otlp

Helm Values Modified

# When opa-otel linked:
enableViolationExport: true
exportBackend: "disk"
audit:
  connection: audit-connection    # Connection CRD name
  channel: audit-channel          # Channel name for disk export
  exportConnection:
    path: /tmp/violations/topics  # Disk write path
    maxAuditResults: 3            # Max violations per file
  exportSidecar:
    name: otel-violation-exporter
    image: otel/opentelemetry-collector-contrib:0.98.0
    args: ["--config=/etc/otel/config.yaml"]
    volumeMounts:
      - /tmp/violations (shared with audit container)
      - /etc/otel (ConfigMap mount)

# When NOT linked:
exportBackend: ""
exportSidecar:
  name: reader
  image: ghcr.io/open-policy-agent/fake-reader:latest

Troubleshooting

  • Audit pod shows 1/1 instead of 2/2 — Missing enableViolationExport: true or exportBackend not set to "disk"
  • Connection CRD has empty name — audit.connection value missing in helm values
  • Sidecar CrashLoopBackOff with port 8888 — OTEL sidecar metrics port conflicting with Gatekeeper manager. Use port 9999.
  • "no files match the configured criteria" — Gatekeeper writes .txt files, not .json. Ensure filelog pattern is **/*.txt
  • OpenSearch mapping errors on resourceLabels — The cleanup processor must delete resourceLabels (dynamic nested k8s labels cause mapping conflicts)
  • No violations appearing — Gatekeeper audit runs every 60s. Check kubectl logs for violation_audited events in the manager container

## The design

29 components. Names are the ones on the diagram.

| Layer | Cells |
|---|---|
| **Applications** | `catalog-svc` (external source code, Django, port 8000) · `portal-frontend` (external source code, Node.js, port 8080) — both `env: production`, 2 replicas |
| **Who reaches them** | `apisix` with 8 routes and an AI gateway sub-component · `crowdsec` with the WAF profile `waf` · `keycloak-operator` · `cert-manager` |
| **Data and events** | `cnpg` with `catalog-db` and `sonarqube` · `kafka` with the topics `bids` and `orders`, a bridge and two node pools · `opensearch` · `valkey` · `seaweedfs` with six buckets |
| **Model** | `vllm` with the model `marketplace-chat` |
| **Data jobs** | `airflow` with the ETL sub-component `catalog-export` |
| **Scale and load** | `keda` with the triggers `api-load` and `shop-load` · `k6` with the suite `shop-journey-r2` |
| **Security** | `opa` with 8 policies · `falco` · `suricata` · `crowdsec` · `openbao` · `external-secrets` · `trivy` · `sonarqube` · `nuclei` |
| **Observability** | `prometheus` (12 scrape links) · `grafana` |
| **Delivery** | `argo-cd` (28 links) · `reloader` |
| **Operations** | `stack-agent` · `fastmcp` |

## The applications

| | catalog-svc | portal-frontend |
|---|---|---|
| Route | `api.<domain>`, rate limit 10000 requests per minute per client address, CORS on, body up to 10 MiB | `shop.<domain>`, rate limit 100 requests per minute, CORS on, body up to 10 MiB |
| WAF | Profile `waf`, `waf_failure_action: passthrough` | The same profile, `passthrough` |
| Gateway login | Off: the application handles its own users | Off |
| Workload hardening | `pod_security`, `container_security`, `read_only_fs`, `drop_capabilities`, `no_privilege_escalation`, `no_host_access`, `seccomp` | The same seven |
| Build gates | `build_gate: enforce`, `sast_gate: enforce`, SonarQube scan through `sonarqube-external_source_code` | The same |
| DAST | `nuclei-external_source_code` | `nuclei-external_source_code` |
| Autoscaling | KEDA trigger `api-load` (`prometheus_query-external_source_code`) | KEDA trigger `shop-load` |

catalog-svc's own links: `external_source_code-db` to `catalog-db`, `external_source_code-swbucket`
to `catalog-images`, `external_source_code-valkey`, `external_source_code-opensearch`,
`external_source_code-topic` to `bids` and to `orders`, and `external_source_code-ai_gateway` to
`ai-gateway`, which links `ai_gateway-model` to `marketplace-chat`. Each one puts its variables into
the application's environment, in the Django form for the database, the cache and the bucket — see
[How a stack fits together](/docs/architecture/#the-layers-and-their-links).

## Security, layer by layer

### At the edge

| Control | On the diagram | What it does here |
|---|---|---|
| Rate limits | `rate_limiting` and `rate_limit_count` on seven of the eight route links (not on Grafana) | APISIX `limit-count` per client address, counted on each gateway replica |
| Web application firewall | CrowdSec `waf` sub-component, linked `waf-external_source_code` to both applications; `apisix-crowdsec` | CrowdSec's AppSec engine (Coraza with the OWASP Core Rule Set, virtual patches, generic rules) checks every request to both applications. The profile runs in `detect`: matches raise alerts, nothing is blocked yet. With `passthrough`, an unreachable WAF lets requests through |
| IP bans | `crowdsec_firewall_bouncer` on, `crowdsec_simulation` off, remediation `ban` for 4 hours | Scenario overflows produce real decisions; the firewall bouncer drops traffic from a banned address on every node. Operator addresses are on `crowdsec_allowlist` so they are never banned |
| Log sources for CrowdSec | `apisix-crowdsec`, `crowdsec-suricata`; collections `suricata`, `base-http-scenarios`, `http-cve` | The agent on every node reads the gateway access log and Suricata's events |

### In the network and at admission

| Control | On the diagram | What it does here |
|---|---|---|
| Network policies | Generated from every link, standard set | One policy per link; the OPA policy `network-policy-enforcement` refuses workloads in namespaces without one |
| Admission policy | `opa` with 8 policy sub-components | `label-deny`, `pod-level-security`, `network-policy-enforcement` and `resource-policy` at `deny`; `image-policy` and `rbac-enforcement` at `warn`; `securitycontext` and `probes` at `dryrun`. Every policy is scoped to the stack label `stacktic.io/stack`. `opa_failure_policy: Ignore`: if Gatekeeper is down, admission does not fail |
| Kafka clients | `mtls` on the Kafka component | Each application linked to a topic gets its own TLS client certificate and ACLs |

### Watching

| Control | On the diagram | What it does here |
|---|---|---|
| Network intrusion detection | `suricata`, linked `suricata-opensearch` | A passive sensor on every node, Emerging Threats Open rules refreshed every 24 hours, alerts and stats shipped to OpenSearch |
| Runtime detection | `falco`, `modern_ebpf` driver, Falcosidekick on | Syscall rules on every node. The design has no `falco-opensearch` link, so Falco's events are not shipped to the SIEM |
| CrowdSec alerts | `crowdsec-opensearch` | Every alert, WAF matches included, in the index `crowdsec-alerts`, with the SIEM dashboards and the new-decision monitor |
| Vulnerability reports | `trivy-opensearch` | Trivy's reports in the SIEM |
| Retention | OpenSearch `retention_hot_days: 7`, `retention_warm_days: 90`, `retention_total_days: 365` | The index lifecycle policy moves the SIEM indices (Falco, APISIX, OPA, audit, OpenTelemetry, Suricata, CrowdSec) to warm after 7 days and deletes them after 365 |
| Metrics | `prometheus-suricata`, `prometheus-crowdsec`, `prometheus-opa` and nine more | Alert rules per component and the provisioned dashboards |

### Secrets

`external-secrets` links `external_secrets-openbao`: a seed Job writes the stack's secrets into
OpenBao, and External Secrets syncs them into the namespaces that use them. `openbao-swbucket`
takes Raft snapshots of OpenBao into a bucket on a schedule. See
[Identity and secrets](/docs/day0/identity-secrets#two-ways-to-hold-a-secret).

### Before anything runs

| Gate | On the diagram | Effect |
|---|---|---|
| Source scan | `build_gate: enforce` on both applications | A finding stops the build |
| Your own rules | `sast_gate: enforce` | Opengrep with the stack's rules stops the build on a match |
| Quality gate | `sonarqube-external_source_code` to both applications, `scan_enabled` on, `enforce_quality_gate` off; `sonarqube-db` | SonarQube scans both applications on every build; a failed quality gate is reported, not blocking, until `enforce_quality_gate` is turned on |
| DAST | `nuclei` linked to both applications, the gateway and the stack agent | One scan contract per link, its runs pushed to the stack agent |
| Evidence | `stack_agent-swbucket` to `compliance-evidence`, `cve_decisions_enabled` on | Compliance evidence files in a bucket; a recorded decision per image vulnerability |

See [Development security](/docs/dev-security/) for the three gates in detail.

|---|---|

| `keda-db` to `catalog-db` | A ScaledObject on the CloudNativePG cluster itself: its instance count follows a PostgreSQL query |
| `keda-topic` to `bids` | Scales the consumers of the topic on their lag |
| `keda-model` to `marketplace-chat` | Scales the model's vLLM runtime |
| k6 `endpoints` sub-component `shop-journey-r2` | A load-test suite of virtual shoppers following a journey, results labelled per step in Prometheus (`prometheus-k6`) and shown in Grafana |
| Airflow `catalog-export`: `db-etl` from `catalog-db`, `etl-swbucket` to `etl-exports` | An ETL job reading the catalog database and writing exports to a bucket |
| `topic-opensearch` from `bids` | A Kafka Connect sink writing every bid into OpenSearch |

## Delivery and operations

| Concern | On the diagram | What it gives this stack |
|---|---|---|
| Delivery | `argo-cd` linked to 28 components · `reloader` | One Application per component, data never deleted by Argo CD, pods restarted when their Secret changes |
| Backups | `cnpg-swbucket`, `opensearch-swbucket`, `openbao-swbucket` | Database backups, OpenSearch snapshots and OpenBao snapshots, each in its own bucket |
| Stack agent | `deploy_access`, `backup_apply_access` and `cve_decisions_enabled` on | Deploys committed branches, runs guarded restore operations, records vulnerability decisions |
| MCP server | `fastmcp` linked to `mcp-client`, `opa`, `stack-agent`, `valkey`, `kafka`; `ai_workflow: spec-kit` | Keycloak login, admission-policy tools, the agent's scans, persistent client storage, Kafka tools, and spec-driven development kits in the application folders |

## What the design deliberately leaves out

These are choices on this diagram, not gaps in the platform:

- The application routes do not use gateway login; the applications authenticate their own users.
- The WAF runs in `detect`. Switching the profile's `waf_mode` to `block` turns matches into
  refusals once the alerts have been reviewed.
- Falco has no OpenSearch link, so its events are not in the SIEM.

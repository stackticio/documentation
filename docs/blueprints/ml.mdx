## What each piece is

| Piece | Role |
|---|---|
| **Experiment tracking and model registry** | Every run, every metric, every artifact, every version |
| **A relational database** | The registry's backend store, and pipeline metadata |
| **Object storage buckets** | Artifacts, curated data, labels, weights, run logs |
| **An orchestrator** | Runs training and apply jobs on demand, on GPU when asked |
| **Your trainer image** | Your own code, built by the platform from your repository |
| **A gateway** | The tracking interface's address, and a login in front of it when you want one |
| **Metrics** | Scrapes the tracking server's own health — not the metrics your runs log |
| **A decision record** | The signature a job reads before it starts, and that a promotion follows |

Without a database and a bucket, the registry falls back to local storage. That fallback is
for development only, and the platform says so rather than letting you discover it.

## The two sub-components that carry the loop

| Sub-component | Side | Who links to it | What the link generates |
|---|---|---|---|
| **Experiment** | Write | Trainers — a job, an asset, or your own code component | The tracking address and the experiment name, so the run lands in the right place |
| **Registered model** | Read | Consumers — an apply job or a serving component | The model address, its name and its alias |

A sub-component-to-sub-component link binds them: *runs logged here become versions there*.
A trainer linked only to the experiment still learns which model to register to, because
the binding is read from the experiment's own record.

Both are created for you when the registry deploys, idempotently, with their tags and
descriptions.

## Promotion is moving one alias

Consumers load the model by **alias**, not by version number. Promotion is a person moving
the alias to another version.

No rebuild. No redeploy. The next run loads the new champion, and rolling back is moving
the alias back.

## Two deliberate human moments

<Cards cols={2}>
  <Card kicker="Before" title="Starting a run">

  </Card>
  <Card kicker="After" title="Promoting a version">
    A promotion changes what your users get. It can be made to follow a signed decision
    rather than a chat message.
  </Card>

Everything between those two moments is automatic. Both signatures are records, and an AI
may propose them but never sign them.

## GPU, queueing and cost

GPU placement comes from the job's attributes — the node selection, the sharing mode, the
memory fraction per model. Heavy periodic work can be admitted through a queue rather than
competing with production workloads, with priority expressed as an attribute.

Because all of it is on the graph, the expensive parts of an ML platform are visible in a
diff and roll back with everything else.

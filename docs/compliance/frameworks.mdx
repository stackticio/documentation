## Capability first, then controls

Before evaluating anything, the scanner builds a **capability picture** from the graph:
does this stack have a policy engine, a certificate authority, a secret store, a SIEM, a
backup mechanism, an identity provider, a gateway, runtime detection.

That picture decides which controls apply and how they can possibly be satisfied. A
requirement about centralised log retention is evaluated differently in a stack that has a
log pipeline than in one that does not — and in the second case the answer is a named gap,
not a silent pass.

## The three modes

| Mode | What it does |
|---|---|
| **Fast** | Collects cluster evidence quickly: workloads, resource types, health, counts |
| **Deep** | Adds hardening scans, admission dry-runs and deeper analysis |
| **Report** | Everything in deep, plus a rendered audit document |

## What the report contains

The generated report is a document an auditor can read without a walkthrough:

<Steps>
  <Step title="An attestation table">
    The result hash, the hash and commit of the declared system it judged, the cluster
    identity and the agent build. The report names the state it was true of.
  </Step>
  <Step title="An executive summary">
    Counts by status, coverage per requirement, and the review coverage.
  </Step>
  <Step title="Per-control findings">
    The automated status, the finding, and the evidence — command, output, result.
  </Step>
  <Step title="The human position">
    Under each control, the recorded review: who signed it, why, and when it expires.
  </Step>
</Steps>

The machine finding and the human position are always shown **side by side**. The automated
status is never replaced by a sign-off.

## From a gap to a plan

A gap is only useful if it says what to do. The framework tools answer three questions in
sequence:

| Question | What comes back |
|---|---|
| Where do I stand? | Overview: counts by status, per-requirement coverage, and what the stack is capable of |
| What is missing? | Gaps with the evidence behind each one |
| What fixes it? | The change to the graph — usually an attribute, sometimes a component or a link |
| What would this component change? | Per-component impact: which controls a given technology moves if you add, remove or reconfigure it |

Because the remediation is a graph change, "we fixed it" is verifiable by re-running the
same scan and comparing the two runs — and the comparison is classified as an improvement
explained by a declared change, not as unexplained movement.

## Two tiers of evidence for ISO 27001

ISO/IEC 27001 names outcomes, never products: "networks shall be segregated", "changes shall follow a
change management procedure". A stack can prove such an outcome with a minimum set of facts, or with
more machinery on top. So 42 of the ISO controls carry two tiers:

| Tier | What it is |
|---|---|
| **Standard** | The floor: the facts that prove the outcome. A stack that has them passes the control |
| **Strong** | The fullest evidence the platform can present — network policies, a GitOps controller, admission policy, intrusion detection, where they apply |

A passing control is graded *Strong* or *Standard*. A stack without the strong set does not read as
failing a control the standard does not ask it for, and a stack that declares the strong set but does
not run it does not read as having it: the auditor-facing note says, per tier, whether the evidence
was presented, declared but not confirmed by this scan, partly in the stack, or not in it. PCI DSS,
which does prescribe segmentation and intrusion detection, keeps one level.

## The HIPAA Security Rule

The third framework is the HIPAA Security Rule, 45 CFR Part 164, Subpart C, as in force. The
scanner judges the 48 standards and implementation specifications of §§ 164.308–164.316: 19
required and 22 addressable implementation specifications, plus the seven standards that carry
none. Every row quotes the regulation's own words, and the report groups them by section —
administrative, physical, technical, organizational, documentation.

What the platform tests from the cluster: backups and disaster recovery, certified restores, audit
controls (the log store and the runtime detector), malware protection, log-in monitoring, password
policy, automatic logoff, unique user IDs, authentication on every gateway route, transmission
security, access authorization, and the periodic evaluation itself. Where the rule fixes no number —
an idle timeout, a password policy — the scan reports the declared value and does not invent a
threshold.

What stays yours: the risk analysis, the policies, the business associate agreements, the workforce
procedures, emergency access, the encryption and integrity of the health records inside your
applications, and the documentation rules. Those rows read *Not Covered* with the reason and the
platform facts that support them, and a named person accepts each one with the document. The
physical safeguards are your hosting provider's and read *N/A* with the provider's attestation
named as the evidence.

An addressable specification is not optional: the rule asks you to implement it, or to document why
it is not reasonable and appropriate and implement an equivalent measure. The scan never drops one.
And there is no HIPAA certificate: the deliverable is the evidence pack and the signed positions.

## DORA

The fourth framework is DORA, Regulation (EU) 2022/2554 on digital operational resilience for the
financial sector, applicable since 17 January 2025. The scanner judges 110 rows: the obligations of
Chapters II to VI addressed to financial entities, one row per paragraph — or per point, where the
points are obligations the platform tests differently — keyed by the citation, such as
`Art.9(4)(b)`. Every row quotes the regulation line for line. Provisions addressed to the supervisory
authorities, options ("may") and the scoping articles are not rows.

What the platform tests: the technical obligations of the ICT risk management framework — updated and
redundant systems, the asset map, monitoring and detection, segmentation, authentication, change and
patch management, backups, restores and logging — the technical half of incident management
(recording, early warning, response mechanisms), and the tests the stack agent performs itself. It
reuses the evidence collectors of the other frameworks, and adds one of its own: the replicas of
every workload and data store.

What stays yours: the governance, the policies, the business continuity plans, incident
classification and reporting, threat-led penetration testing, the third-party contracts and the
register of information. Those rows read *Not Covered* with the reason and the platform facts that
support them, and a person accepts them with the document. Paragraphs addressed to one type of entity
only — central securities depositories, central counterparties, data reporting service providers,
microenterprises — read *N/A* with the entity type named; an entity of that type rejects the N/A and
decides the row. There is no DORA certification: compliance is assessed by the competent authority,
and the deliverable is the evidence pack.

The scan runs in the same [three modes](#the-three-modes) as the others: fast (cluster evidence, under a
minute), deep (adds the hardening scans, a few minutes) and report (deep, plus the rendered document).

## Continuous, not annual

A compliance position computed once a year describes a system that no longer exists.

Framework scans participate in the same schedule, delta and attestation machinery as every
other scan: they can run continuously, every run is chained to the previous one, a
regression is confirmed by a re-run before anyone is alerted, and a labelled run becomes
the baseline that drift is measured against.

<Hero eyebrow="Compliance" title="Compliance is not a document. It is a measurement with a signature on it.">
Most of what a framework asks for is already a property of how the system was built. The
rest is a position a person has to take. Stacktic automates the first, records the second,
and makes both checkable.
</Hero>

## Three layers, and none of them is a spreadsheet

<Cards>
  <Card kicker="1 · Generated" title="The control is built in">
    Segmentation, least-privilege access, encrypted credentials, TLS everywhere, admission
    policy, audit logging and backup are produced from the graph — so the control exists
    because of how the system was generated, not because someone configured it afterwards.
  </Card>
  <Card kicker="2 · Measured" title="The control is proven">
    Every control is validated against the running cluster with real command evidence:
    what was queried, what came back, and what that means. Not a checkbox, and not a
    metadata inference.
  </Card>
  <Card kicker="3 · Positioned" title="The gap is owned">
    Where a control cannot be met automatically, a named person records a position —
    confirmed gap, compensating control, not applicable, or accepted risk with an expiry
    date. That position is the audit-defensible artefact.
  </Card>
</Cards>

## What "evidence" means here

Every control returns the command that ran, its output, and the result derived from it.

```json
{
  "id": "A.5.2",
  "title": "Information security roles and responsibilities",
  "runtime_status": "In Place",
  "finding": "RBAC verified: 23 role bindings, compliance score 85%",
  "evidence": [{
    "command": "kubectl get rolebindings --all-namespaces + declared vs actual",
    "output": "Expected: 30 RBAC resources, Found: 23, Missing: 7 ...",
    "result": "RBAC score=85% expected=30 found=23 missing=7"
  }]
}
```

An auditor can re-run the command. That is the point.

## What gets verified from the cluster

| Area | Evidence collected |
|---|---|
| Admission policy | Engine health, constraint templates, constraints, live violations, dry-run admission tests |
| Network policy | Policy count, default-deny per namespace, real connection probes |
| Access control | Role bindings, privileged holders, wildcard roles, score |
| Transport security | Certificate authority health, certificates ready and expiring, issuers |
| Secrets | Store seal state, synchronisation status of every external secret |
| Monitoring | Metrics health and targets, alert rules, dashboards, log pipeline, tracing, SIEM |
| Runtime security | Vulnerability reports, critical findings, runtime detection, signature policy |
| Delivery | Application count, sync status, drift |
| Recovery | Schedules, recent successful runs, and whether they hold data |
| Identity and gateway | Provider and gateway health, published route inventory |

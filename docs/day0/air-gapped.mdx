A cluster with no internet access cannot pull a single public image. Switch the stack to
air-gapped and the build inventories every image it uses, writes the script that copies
them into your registry, and rewrites every manifest to pull from there.

## Turn it on

Air-gapped mode is a [section value](/docs/platform/sections), not a different design:

<Steps>
  <Step title="Point the system at your registry">
    On the system's configuration page, set the registry host and project. That registry
    is where every image will be pulled from — the same one in-cluster builds push to.
  </Step>
  <Step title="Set air_gapped to true">
    In <strong>Sections</strong>, set the system attribute <code>air_gapped</code> to
    <code>true</code>.
  </Step>
  <Step title="Build">
    The build runs three extra steps after the other components have rendered: inventory,
    migration script, rewrite.
  </Step>
</Steps>

The graph does not change. The same components, links, policies and validation surface
generate; only where images are pulled from moves.

## What the build produces

| Output | What it is |
|---|---|
| `versioning/versions.json` · `versions.md` | Every image the stack references, and every file that references it |
| `versioning/bom.json` · `bom.xml` | A bill of materials for the stack's images |
| `versioning/migration/migrate.sh` | The script that copies every image into your registry |
| Rewritten kustomizations | Every component's deploy **and** build kustomization pulls from your registry — `<host>/<project>/<image>`, keeping the original tag or digest |
| `airgap-images-config.yaml` | For images held in a custom resource field — a monitoring server's image, a database cluster's image — the field is rewritten too |
| `airgap-patch-*.yaml` | For images an operator reads from its environment or arguments, a patch on that operator's workload |

The rewrite is idempotent: building again after a registry change updates the entries in
place.

## Copy the images, once

`migrate.sh` copies registry to registry, keeping every architecture of a multi-platform
image. Run it once, before the first apply, from a machine that can reach **both** the
public registries and yours — not from inside the isolated network:

```bash
export REGISTRY_PASSWORD=<your registry password>   # or type it when prompted
versioning/migration/migrate.sh
```

It needs Docker with Buildx, logs in to your registry, and reports how many images
succeeded and failed. It is safe to run again: a second run retries what failed. It also
warns when two source images would land on the same target name.

Then apply the stack as usual: every image the rewrite covered is pulled from your
registry.

## Before you rely on it

:::caution Allow your registry in the admission policy
An image policy in the stack admits only the registries listed on it, and air-gapped mode
does not change that list. Add your registry to the policy's allowed registries, or the
rewritten workloads are refused at admission.
:::

Some images cannot be rewritten automatically, and the build log names each one it meets:

- image fields shaped as a mapping of registry and name rather than one string;
- images embedded deeper inside custom resources, with no generic patch;
- short image names inside an operator's environment or arguments;
- images compiled into an operator itself.

Handle those on the component, and check the log after the first air-gapped build.

The AI interface needs its knowledge repository inside the network too: mirror it and
point the MCP server at the mirror — see [The knowledge layer](/docs/mcp/knowledge).

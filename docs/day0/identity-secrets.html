Identity and secrets

Access
People and credentials are part of the graph

A user is not something you create in an application. It is an attribute of the system, and it propagates to every application the graph says it should reach.

Users and groups are declared​

System users live as lines on the identity provider's client sub-component. Groups live on the identity provider itself. Both are ordinary attributes, so both are versioned with the stack, duplicated with it into another environment, and rolled back with it.

Declared asShape
A userusername : email : password : first name : last name plus optional flags such as multi-factor
A groupname : email : members

On the next build and deploy, synchronisation jobs derive the actual accounts from those lines, and single sign-on carries the identity into every application that has an identity link.

The username is the durable key. Renaming a person changes their display name; it does not create a second account.

Creating users inside an application is drift

An account created directly through an application's own admin interface is invisible to the graph, skipped by the synchronisation jobs, and silently diverging from the declared system. It will appear to work, and then quietly stop matching everything else.

Onboarding and offboarding go through the platform — which is exactly what the MCP user_lifecycle tool does, including telling you what will propagate where.

Single sign-on is a link​

An application does not get a login because someone configured one. It gets a login because there is a link between it and the identity provider — and that link generates the OIDC client, the client secret, the redirect URIs and the application-side configuration together.

Add the link, and the application is behind a login. Remove it, and it is not. There is no third state where the client exists but the application does not know about it.

Two ways to hold a secret​

DefaultEncrypted in the repository

Credentials are generated per instance and encrypted at rest in your stack repository. Decryption is local and offline, with a key you hold. Nothing external is required, and the stack installs in an air-gapped environment unchanged.

OptionalSourced from a secret store

Components can instead pull their secrets from an external secret store at runtime. The component declares that it wants this; the operator and the store are components of the stack like anything else.

Both are expressible on the same graph, and the choice is per component rather than all-or-nothing.

A store token is a runtime credential

When secrets come from an external store, the store's access token is held as a design-time attribute. Re-initialising the store therefore leaves the stack presenting a token that no longer exists — and the failure is indirect: the store goes invalid, every secret stops syncing, workloads cannot start, and the symptom you actually see is an application error with no obvious link to secrets.

Two valid recoveries: refresh the attribute with the new token, or switch the affected components back to generating their secrets locally.

Every instance gets its own credential​

A catalog default is written for one instance. The moment a component owns a second sub-component of the same kind — two buckets, three databases, four clients — each one needs its own name, user and secret.

This is enforced at generation time. Two buckets sharing an access key do not produce a subtly wrong stack; they produce a build that stops and tells you which value has to differ.

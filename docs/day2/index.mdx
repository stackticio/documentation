<Hero eyebrow="Day 2" title="AI cannot run operations by improvising. It can run them inside a framework.">
The stack agent is deployed into your stack, reads the same metadata the build produced,
and turns every declaration into something measurable. It is the interface between an AI
and your runtime — and the reason an AI is allowed near it.
</Hero>

## What it is

One component, one API, scoped to one stack. It carries the tooling to reach every
technology in the stack, and it knows the topology because it reads the graph rather than
discovering it.

## Why a separate agent

Because a claim made by the thing that generated the system is not evidence.

The build says what should exist. The agent runs inside the cluster, with its own view, and
answers what does. When the two disagree, the disagreement is the finding — and it is
attributed: to a declared change you made, to an environment change, or to drift nobody
asked for.

## How you reach it

Three ways, same engine:

| Through | For |
|---|---|
| **Your AI client, over MCP** | The normal way. Ask a question, get an answer with evidence |
| **The dashboard** | A visual surface for scans, scores, timelines, evidence export and audit-friendly printing |
| **The HTTP API** | Automation and CI. Every scan, query and report is an endpoint |

All three are optional surfaces over the same measurements, so a number shown in the
dashboard, quoted by the model and exported for an auditor is the same number.

## What it is deliberately not

It is not a GitOps drift detector comparing a manifest to a live object. It compares the
**outcomes of executed checks** over time, and explains each change. A control that passed
last week and fails today is a finding with a first-seen date, an age, a reopen count and
a classification — not a red line in a diff.

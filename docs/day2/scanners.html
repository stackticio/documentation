Scanners

Measure
Scans that know what your system is supposed to be

A generic scanner reports what it finds. These scanners compare what they find against the graph — so a missing network policy is reported against the link that should have produced it, and a finding comes with the attribute that fixes it.

Every scanner has a light mode for fast, frequent checks and a full mode that actively probes. Every run is scored, stored and hash-chained.

The scanners​

Findings are actionable, not descriptive​

A finding from a generic tool tells you a property of a Kubernetes object. A finding here tells you which part of your declared system is not holding, and what changes it.

The remediation is expressed as the attribute to change on the graph — not a patch to hand-apply, because a hand-applied patch is drift that the next build will remove.

Over-enforcement is a finding too​

The admission policy scan does not only ask whether a policy blocks what it should. It also asks whether it blocks things it should not.

A constraint that rejects legitimate workloads is a production incident waiting for the next deploy, and it is invisible to any check that only counts violations. Classifying a constraint as over-enforcing is the difference between a policy baseline you can actually turn on and one that stays in audit mode forever.

Running them​

ThroughHow
Your AI clientscan(scanner=..., mode=...) — present the score, the summary, the findings by severity, and the fixes
The dashboardRun any scan, watch it progress, export the evidence, print an audit-friendly report
The APIOne endpoint per scan, with a mode parameter
On a scheduleInside the agent, per scan type — see Evidence and drift

Scans run as background tasks and survive navigation, so a long full scan is not tied to a browser tab or a conversation staying open.

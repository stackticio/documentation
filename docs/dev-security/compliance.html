Which control reads what

Prove
The test reads the record, not the diagram

A gate that is switched on is a configuration. A gate that ran, on a dated commit, with a verdict the agent kept, is evidence. The compliance scans only count the second kind — which is why the same page that shows you a gap also shows you what the auditor's scan will say.

What the tests say about a half-done chain​

The tests are written to refuse the comfortable reading:

  • a no_targets DAST run (the application answered 502) is not an assessment — the 365-day and 90-day rules count only completed runs;
  • a gate set to report that printed findings is a finding in the Builds & Gates scan ("findings that were only printed"), not a pass;
  • a contract whose schedule is empty and that nobody started shows as "no run yet", and the control stays Not In Place until it runs;
  • the DAST Coverage page previews these verdicts with the same rules, so the gap is closed before the audit scan is run, not explained afterwards.

What automated testing does not claim​

  • Not an ASV scan. PCI DSS 11.3.2 requires an Approved Scanning Vendor; the DAST runs are the organisation's own external scans and the after-change scans of 11.3.2.1. The test says so in its output.
  • Not a penetration test. 11.4 is human-led. The Penetration Test tab runs the WSTG checklist and reads the DAST runs; checks that need judgement or provisioned identities are reported as manual, never as a fabricated pass.
  • Not a code review. The quality gate analyses code; it does not replace the independent review 6.2.3.1 describes for manual reviews.

For the training programme​

Modules on the pipeline, dependencies, secrets and self-service tools map to this chapter one to one: the source scan is Gate 1, the SonarQube code gate is Gate 3, "run the DAST after you expose or change an endpoint" is the nuclei-<app> contract and the DAST Coverage tab, and the evidence rules are the records described here.

## 1 · Declare

A stack is a directed graph held by the platform. Three kinds of node, one kind of edge:

| Element | What it is | Examples |
|---|---|---|
| **Component** | A technology instance in the stack | your application, a PostgreSQL cluster, a gateway, an identity provider, a vector store |
| **Sub-component** | A resource that a component owns | a database, a bucket, a Kafka topic, a RabbitMQ queue, an OIDC client, a served model |
| **Link** | A typed edge between two nodes | `fastapi-cnpg`, `apisix-langflow`, `prometheus-mongodb` |
| **Attribute** | A value on a component, a sub-component or a link | namespace, version, replica count, retention, whether OIDC is on |

A link type is always `sourceType-targetType`. That string is the contract: it selects
which generation logic runs, which files appear, and which values are carried across.

Attributes live in exactly three places — on the component, on the sub-component, or on
the link. Nothing else carries configuration, which is why the graph alone is enough to
regenerate the whole system.

## 2 · Generate

A build renders one template per component and aggregates the results into a single
GitOps repository.

<Steps>
  <Step title="Parse the graph">
    The diagram becomes a typed object model: components, sub-components, links indexed by
    source and by target.
  </Step>
  <Step title="Resolve relationships">
    Before a component renders, its inbound and outbound links are resolved. A template
    asks "is there a link of type X into me?" and generates accordingly — the consumer's
    environment variables, the producer's credentials, the route, the policy.
  </Step>
  <Step title="Render every component">
    Components render in parallel, each into its own tree. Helm charts are rendered to
    plain YAML so the output is readable and diffable rather than a chart you must trust.
  </Step>
  <Step title="Aggregate">
    Per-component output is merged into one repository layout — <code>k8s/build</code>,
    <code>k8s/deploy</code>, overlays per environment, docs, scripts — and the stack's own
    metadata is written alongside it.
  </Step>
  <Step title="Commit">
    The result is committed to your stack repository. Your own edits to marked files are
    merged rather than overwritten; a conflict stops the push instead of committing
    markers.
  </Step>
</Steps>

### Incremental builds

A full build regenerates everything. A **push** does not: it diffs the graph against the
last pushed state, resolves which files each changed attribute can possibly affect through
a per-template impact map, and re-renders only those files. The build log ends with the
exact `kubectl apply` lines for what changed.

## 3 · Validate

Generation says what should exist. Validation proves what does.

The **stack agent** is deployed into the stack and reads the same `stack-metadata.yaml`
the build produced. Every declared relationship is proven layer by layer — was it rendered
into the consumer, did the credential arrive, is the port reachable, does the role permit
it, does the target actually answer with that credential — and the verdict names the layer
that failed rather than a generic red cross.

The same engine runs scored security and compliance scans, and stores every run as a
hash-chained record with the metadata commit it was measured against.

→ [Day 2 — operate and prove](/docs/day2/) · [Evidence and attestation](/docs/day2/evidence)

## 4 · Operate

The stack is the unit of version. Not a manifest, not a chart — the whole graph plus every
attribute on it.

| Operation | What it means |
|---|---|
| **Snapshot** | The full topology and configuration at a point in time |
| **Duplicate** | The same system as a second environment, with its own values |
| **Roll back** | The entire stack returns to a previous state, relations included |
| **Compare** | A diff between two versions of the system, not of a file |
| **Migrate** | A component version moves, and everything that depends on it moves with it |

Because a change is expressed on the graph, its consequences are computable before it is
applied. Asking "what does this attribute touch" returns the files, the components
downstream, and the dependents that will need attention — which is what makes it safe to
let an AI propose the change.

Start with the MCP initiator stack

Quickstart
Build the stack that builds the stacks

Six components. Once they are running, your AI client has an authenticated interface to the platform, the live graph and the cluster — and every later stack can be designed, generated, deployed and proven through it.

Why this is the first thing you build​

You could design a full application stack by hand and connect the AI afterwards. It is the wrong order. The initiator stack is small, it is generic, and it hands the model the three things it needs before it can be useful: the catalog (what can exist), the graph (what does exist) and the runtime (what is actually true).

Everything after this is a conversation.

What it contains​

ComponentRole in the initiator stackRequired
Certificate managerTLS for the gateway, issued and renewed automaticallyYes
API gatewayThe public entry point; publishes the MCP endpoint on a subdomainYes
Identity providerThe OIDC client your AI client authenticates againstYes
MCP serverThe AI interface itselfYes
Stack agentTopology queries, validation, scans — the MCP's runtime handsYes
CachePersistent OAuth state, so the connector survives a pod restartStrongly recommended

The links that make it work​

Four typed links turn six separate components into a working interface. Draw them and the configuration is generated; leave one out and the corresponding capability is simply absent.

LinkWhat it produces
gateway → MCP serverThe public HTTPS route, TLS, and the host the connector talks to
MCP server → stack agentThe runtime hands: topology queries, tests, scans, evidence
MCP server → identity clientOIDC login for the connector, with redirect URIs already correct
MCP server → cachePersistent OAuth state across restarts

Bring it up​

Draw the six components and the four links

Set a namespace and a subdomain for the gateway, and a domain for the stack. Everything else can stay on catalog defaults for a first run.

Build

The platform renders every component, resolves the links, and commits the result to your stack repository — manifests, overlays, build pipelines, policies and the stack-metadata.yaml that describes the graph.

Build the images in the cluster

Container images are built in-cluster from the generated build manifests. No local Docker daemon is involved.

kubectl apply -k k8s/build/base/<component>/
Deploy

Apply the generated deploy tree. The same command is safe to repeat — re-applying is the normal way to move the cluster to a new stack version.

kubectl apply -k k8s/deploy/base/<component> --server-side=true --force-conflicts=true
Connect your AI client

Point it at the MCP endpoint published by the gateway and complete the OAuth login. See Connect a client.

Ask it to orient itself

A good first message is simply: “Describe this stack and tell me what it can do.” The model will read the topology, list its own available tools, and tell you which capabilities are present and which links would add more.

What you can do the moment it is up​

DesignPaste a specification

Hand the model your data or product spec. It asks the smallest set of questions that change the drawing, then proposes a complete stack from the real catalog.

OperateAsk what is wrong

Scans, link proofs and graph traversal answer “is my stack healthy” with evidence rather than an opinion.

HardenAsk what to tighten

The model enumerates the exact attributes that change the posture and what stays running when they flip.

ProveAsk for the compliance position

Framework coverage, gaps, and the evidence behind each control, straight from the cluster.

Growing from here​

Adding your application is one more component plus its links. The model proposes them; you approve; the build regenerates everything the change touches — including the network policies, the route, the secrets and the monitoring that the new edges imply.

<Hero eyebrow="Quickstart" title="Build the stack that builds the stacks">
Six components. Once they are running, your AI client has an authenticated interface to
the platform, the live graph and the cluster — and every later stack can be designed,
generated, deployed and proven through it.
</Hero>

## Why this is the first thing you build

You could design a full application stack by hand and connect the AI afterwards. It is the
wrong order. The initiator stack is small, it is generic, and it hands the model the three
things it needs before it can be useful: the **catalog** (what can exist), the **graph**
(what does exist) and the **runtime** (what is actually true).

Everything after this is a conversation.

## What it contains

| Component | Role in the initiator stack | Required |
|---|---|---|
| **Certificate manager** | TLS for the gateway, issued and renewed automatically | Yes |
| **API gateway** | The public entry point; publishes the MCP endpoint on a subdomain | Yes |
| **Identity provider** | The OIDC client your AI client authenticates against | Yes |
| **MCP server** | The AI interface itself | Yes |
| **Stack agent** | Topology queries, validation, scans — the MCP's runtime hands | Yes |
| **Cache** | Persistent OAuth state, so the connector survives a pod restart | Strongly recommended |

## The links that make it work

Four typed links turn six separate components into a working interface. Draw them and the
configuration is generated; leave one out and the corresponding capability is simply
absent.

| Link | What it produces |
|---|---|
| gateway → MCP server | The public HTTPS route, TLS, and the host the connector talks to |
| MCP server → stack agent | The runtime hands: topology queries, tests, scans, evidence |
| MCP server → identity client | OIDC login for the connector, with redirect URIs already correct |
| MCP server → cache | Persistent OAuth state across restarts |

## Bring it up

<Steps>
  <Step title="Draw the six components and the four links">
    Set a namespace and a subdomain for the gateway, and a domain for the stack. Everything
    else can stay on catalog defaults for a first run.
  </Step>
  <Step title="Build">
    The platform renders every component, resolves the links, and commits the result to
    your stack repository — manifests, overlays, build pipelines, policies and the
    <code>stack-metadata.yaml</code> that describes the graph.
  </Step>
  <Step title="Build the images in the cluster">
    Container images are built in-cluster from the generated build manifests. No local
    Docker daemon is involved.

```bash
kubectl apply -k k8s/build/base/<component>/
```
  </Step>
  <Step title="Deploy">
    Apply the generated deploy tree. The same command is safe to repeat — re-applying is
    the normal way to move the cluster to a new stack version.

```bash
kubectl apply -k k8s/deploy/base/<component> --server-side=true --force-conflicts=true
```
  </Step>
  <Step title="Connect your AI client">
    Point it at the MCP endpoint published by the gateway and complete the OAuth login.
    See <a href="/docs/mcp/connect">Connect a client</a>.
  </Step>
  <Step title="Ask it to orient itself">
    A good first message is simply: <em>&ldquo;Describe this stack and tell me what it can
    do.&rdquo;</em> The model will read the topology, list its own available tools, and tell
    you which capabilities are present and which links would add more.
  </Step>
</Steps>

## What you can do the moment it is up

<Cards>
  <Card kicker="Design" title="Paste a specification">
    Hand the model your data or product spec. It asks the smallest set of questions that
    change the drawing, then proposes a complete stack from the real catalog.
  </Card>
  <Card kicker="Operate" title="Ask what is wrong">
    Scans, link proofs and graph traversal answer &ldquo;is my stack healthy&rdquo; with
    evidence rather than an opinion.
  </Card>
  <Card kicker="Harden" title="Ask what to tighten">
    The model enumerates the exact attributes that change the posture and what stays
    running when they flip.
  </Card>
  <Card kicker="Prove" title="Ask for the compliance position">
    Framework coverage, gaps, and the evidence behind each control, straight from the
    cluster.
  </Card>
</Cards>

## Growing from here

Adding your application is one more component plus its links. The model proposes them; you
approve; the build regenerates everything the change touches — including the network
policies, the route, the secrets and the monitoring that the new edges imply.

Tool surface

Reference
What the model can actually do

Most tools are dispatchers: one tool, an action enum, and a built-in help action that returns the full usage guide for every capability it covers. Nothing here has to be memorised — the model asks for help instead of guessing parameters.

The tool list is a description of your architecture

Per-technology tools register only when the matching link exists. A stack without a vector store has no vector-store tools. Draw the link, build, deploy — the capability appears.

Orientation — where the stack is, and whether the server works​

ToolWhat it answers
workflowThe guided journey: measures where the stack is — design, build, install, automate, secure, prove, operate — and returns one next step with the exact call to make, the questions to ask you first, and the docs page that explains it. The server tells the model to call it first in a conversation and after every milestone
server_infoWhat this server can do right now: knowledge repository access, platform account, stack agent, cluster access, Argo CD, and the tool modules that loaded
self_checkTests every credential and connection the server runs on, live, and names the attribute that fixes what is broken
pingWhether the server answers at all

Knowledge — what the platform can express​

ToolWhat it answers
knowledgeComponent and link deep knowledge, search, recipes, recommendations, curated patterns from working stacks, and ad-hoc access to the knowledge files
knowledge(action='impact')Which generated files and downstream components a given attribute touches
knowledge(action='validate')Whether a component in the stack is configured the way its template actually expects
knowledge(action='refresh')Pull the latest platform knowledge without redeploying anything
platform_gapA need the catalog cannot express: prove it is really missing, cover it with the flexibility that exists, and report it to the platform team instead of improvising

Graph — what your system is​

ToolWhat it answers
stack_graphThe declared graph, read from your stack repository with credentials redacted — components, links, and the link types you have not drawn yet. Always available, even without a stack agent
topology_infoStructure, components, links, available fields — the first call in most conversations
query_topologyA filtered query over the graph with field selection
graphBlast radius, dependency path, search by context, health map, data flow, service contract
investigateMulti-hop diagnosis across knowledge and runtime for a symptom or a question
stack_repoBrowse, read and search the generated manifests — the ground truth of what was produced

blast_radius is the one to insist on. Before any change, it returns what depends on the target, how badly, and what the recommended order of operations is.

Runtime — what is actually true​

ToolWhat it does
stack_testRuns real end-to-end validation against the live topology: connections, credentials, certificates, routes
scanScored scans through the stack agent: penetration test, link validation, admission policy, network policy, Kubernetes hardening, RBAC, secrets, configuration posture, vulnerability sweep, PCI DSS and ISO 27001
evidenceThe attestation trail: versioned runs, hash chains, deltas, finding memory
backupWhat is protected, what can be proven, restore points, and guarded day-2 operations
cveVulnerability findings from two sources that are never added together — weaknesses in your own code, and known vulnerabilities in images — with the decision recorded for each

kubectl_*Last resort only — pod status, events, logs, restarts. Never used for discovery or scanning

Write — change the declared system​

These are the tools that make the model an operator rather than an advisor. Every one of them writes to the graph, never to the cluster directly.

Drawing a design. The model assembles a working diagram in its session and pushes it in one step:

ToolWhat it does
stacktic_loginSession for the platform account, as a specific user
stacktic_get_components_* · stacktic_get_selected_components_*The catalog pieces for a design: component types, the links they allow, their attributes, their sub-components, and the reason each one matters
stacktic_describeEvery attribute of one component type: its key, type, default, options, the pattern free text must match, and whether it is a secret
stacktic_new_diagram · stacktic_get_diagramOpen a working diagram seeded from the live system, and read it back
stacktic_add_cell · stacktic_add_link · stacktic_add_many · stacktic_add_zoneAdd components, sub-components, links and labelled background zones to the working diagram
stacktic_update_cell · stacktic_remove_cellFix or remove one cell without redrawing the graph
stacktic_validate_diagramCheck the working diagram against the rules the platform enforces on push, before pushing
stacktic_set_systemPush the working diagram. The pushed graph replaces the system, which is why the working diagram always starts from the live one
stacktic_get_systemRead a system as it is stored

Changing what exists.

ToolWhat it changes
stacktic_attrOne attribute, several attributes, or a link attribute
stacktic_systemBuild, build logs, duplicate, delete, synchronise with the catalog, and removing a component or a link
stacktic_rationaleThe Knowledge page — list the papers, read or write the rationale stored on a component, sub-component or link
design_doctorWhy a push, an attribute update or a build was refused, in plain words, and which cell or attribute fixes it

The workflow the server enforces is always the same: get the current value, show it, state the blast radius, ask, then change. A build never runs without explicit confirmation.

Application development​

ToolWhat it does
list_repos · clone_repo · browse_files · read_file · search_code · get_project_structure · get_entry_points · get_runtime_context · get_security_postureRead the code of the application components linked to the server — the ground truth for behaviour
write_file · delete_file · diff · create_branch · commit_and_push · discard_changesChange that code on a branch and push it
stack_repo_writeWrite a new application into the stack repository itself — one folder per application under apps/, with its own Dockerfile — using the token the platform already holds
spec_kitSpec-driven development for application components, with a constitution generated from the actual stack. Switched on by the MCP component's ai_workflow attribute

The code tools appear for each application component the MCP server is linked to.

Before recommending application work, the model checks what specifications and tasks are already in flight, so two sessions do not design the same feature twice. Shared project state lives in your repositories, not in a client's private memory.

Guided prompts​

The server also ships prompts — starting points a client can offer directly to a person who does not want to think in tools.

Orientationstart_here · explain_stack

What this stack is, what it runs, and what the model can do with it.

Journeynext_step · install_my_stack · add_gitops

The one next thing to do; how a built stack reaches the cluster; and adding automated delivery — always asking scope and mode first.

Gapsrequest_platform_change

Something the catalog cannot express: prove it, cover it with what exists, and send the suggestion to the platform team.

Builddeploy_my_app · add_to_my_app

Take an application from a repository or a description to a running, wired stack.

Assureis_my_stack_ok · validate_my_stack · run_validation

Health, end-to-end validation, and a scoped validation run.

Secureharden_my_stack · security_audit

The exact attributes that change the posture, and a full audit with evidence.

Diagnoseincident_response · diagnose_component · check_logs

From a symptom to a cause, using the graph rather than a guess.

Designrecommend_architecture · trace_data_flow

A grounded architecture proposal, and where data actually goes.

Scheduled autonomous work​

The MCP server can also run unattended. Two sub-component types on the MCP server turn a conversation into a standing job:

Sub-componentWhat it is
agentA configured AI worker: which model, which tool categories it may use, its budget
ai_taskA task with a schedule, a prompt, a notification target, and optional chaining to another task

Tasks run on a cron expression inside the stack, call the same MCP tools a human conversation would, track token usage and cost per task, and report by webhook or email. Chained tasks pass their result to the next one. This is how a nightly compliance run, a weekly dependency review or a continuous drift watch is expressed — as part of the stack, versioned with it.

ToolWhat it does
dark_factory_statusEvery agent's configuration and every task's state, last run and result
dark_factory_historyThe run history of one task
dark_factory_run_nowRun a task immediately, skipping its schedule; a chain continues on success
dark_factory_toggle_agentSwitch an agent on or off at runtime, without a redeploy
dark_factory_costToken usage and estimated cost per task, and in total

<Hero eyebrow="Reference" title="What the model can actually do">
Most tools are dispatchers: one tool, an action enum, and a built-in help action that
returns the full usage guide for every capability it covers. Nothing here has to be
memorised — the model asks for help instead of guessing parameters.
</Hero>

:::note The tool list is a description of your architecture
Per-technology tools register **only when the matching link exists**. A stack without a
vector store has no vector-store tools. Draw the link, build, deploy — the capability
appears.
:::

## Orientation — where the stack is, and whether the server works

| Tool | What it answers |
|---|---|
| `workflow` | The guided journey: measures where the stack is — design, build, install, automate, secure, prove, operate — and returns **one** next step with the exact call to make, the questions to ask you first, and the docs page that explains it. The server tells the model to call it first in a conversation and after every milestone |
| `server_info` | What this server can do right now: knowledge repository access, platform account, stack agent, cluster access, Argo CD, and the tool modules that loaded |
| `self_check` | Tests every credential and connection the server runs on, live, and names the attribute that fixes what is broken |
| `ping` | Whether the server answers at all |

## Knowledge — what the platform can express

| Tool | What it answers |
|---|---|
| `knowledge` | Component and link deep knowledge, search, recipes, recommendations, curated patterns from working stacks, and ad-hoc access to the knowledge files |
| `knowledge(action='impact')` | Which generated files and downstream components a given attribute touches |
| `knowledge(action='validate')` | Whether a component in the stack is configured the way its template actually expects |
| `knowledge(action='refresh')` | Pull the latest platform knowledge without redeploying anything |
| `platform_gap` | A need the catalog cannot express: prove it is really missing, cover it with the flexibility that exists, and report it to the platform team instead of improvising |

→ [The knowledge layer](/docs/mcp/knowledge)

## Graph — what your system is

| Tool | What it answers |
|---|---|
| `stack_graph` | The declared graph, read from your stack repository with credentials redacted — components, links, and the link types you have not drawn yet. Always available, even without a stack agent |
| `topology_info` | Structure, components, links, available fields — the first call in most conversations |
| `query_topology` | A filtered query over the graph with field selection |
| `graph` | Blast radius, dependency path, search by context, health map, data flow, service contract |
| `investigate` | Multi-hop diagnosis across knowledge and runtime for a symptom or a question |
| `stack_repo` | Browse, read and search the generated manifests — the ground truth of what was produced |

`blast_radius` is the one to insist on. Before any change, it returns what depends on the
target, how badly, and what the recommended order of operations is.

## Runtime — what is actually true

| Tool | What it does |
|---|---|
| `stack_test` | Runs real end-to-end validation against the live topology: connections, credentials, certificates, routes |
| `scan` | Scored scans through the stack agent: penetration test, link validation, admission policy, network policy, Kubernetes hardening, RBAC, secrets, configuration posture, vulnerability sweep, PCI DSS and ISO 27001 |
| `evidence` | The attestation trail: versioned runs, hash chains, deltas, finding memory |
| `backup` | What is protected, what can be proven, restore points, and guarded day-2 operations |
| `cve` | Vulnerability findings from two sources that are never added together — weaknesses in your own code, and known vulnerabilities in images — with the decision recorded for each |
| `lifecycle` | Upgrade and migration status and plans per component, from declarative recipes |
| `kubectl_*` | Last resort only — pod status, events, logs, restarts. Never used for discovery or scanning |

## Compliance

| Tool | What it does |
|---|---|
| `pci` | Pre-formatted PCI position: overview, per-requirement detail, gaps, per-component impact |
| `opa_setup` | Plans and applies an admission-policy baseline that fits this topology, with the namespace carve-outs the stack actually needs |
| `opa_*` | Constraint templates, constraints, live violations, compliance summary |
| `scan(config)` | Configuration posture over the declared attribute surface, from declarative rules |

→ [Compliance automation](/docs/compliance/)

## Write — change the declared system

These are the tools that make the model an operator rather than an advisor. Every one of
them writes to the graph, never to the cluster directly.

**Drawing a design.** The model assembles a working diagram in its session and pushes it
in one step:

| Tool | What it does |
|---|---|
| `stacktic_login` | Session for the platform account, as a specific user |
| `stacktic_get_components_*` · `stacktic_get_selected_components_*` | The catalog pieces for a design: component types, the links they allow, their attributes, their sub-components, and the reason each one matters |
| `stacktic_describe` | Every attribute of one component type: its key, type, default, options, the pattern free text must match, and whether it is a secret |
| `stacktic_new_diagram` · `stacktic_get_diagram` | Open a working diagram seeded from the live system, and read it back |
| `stacktic_add_cell` · `stacktic_add_link` · `stacktic_add_many` · `stacktic_add_zone` | Add components, sub-components, links and labelled background zones to the working diagram |
| `stacktic_update_cell` · `stacktic_remove_cell` | Fix or remove one cell without redrawing the graph |
| `stacktic_validate_diagram` | Check the working diagram against the rules the platform enforces on push, before pushing |
| `stacktic_set_system` | Push the working diagram. The pushed graph **replaces** the system, which is why the working diagram always starts from the live one |
| `stacktic_get_system` | Read a system as it is stored |

**Changing what exists.**

| Tool | What it changes |
|---|---|
| `stacktic_attr` | One attribute, several attributes, or a link attribute |
| `stacktic_system` | Build, build logs, duplicate, delete, synchronise with the catalog, and removing a component or a link |
| `stacktic_rationale` | The Knowledge page — list the papers, read or write the rationale stored on a component, sub-component or link |
| `design_doctor` | Why a push, an attribute update or a build was refused, in plain words, and which cell or attribute fixes it |

The workflow the server enforces is always the same: **get the current value, show it,
state the blast radius, ask, then change.** A build never runs without explicit
confirmation.

## Application development

| Tool | What it does |
|---|---|
| `list_repos` · `clone_repo` · `browse_files` · `read_file` · `search_code` · `get_project_structure` · `get_entry_points` · `get_runtime_context` · `get_security_posture` | Read the code of the application components linked to the server — the ground truth for behaviour |
| `write_file` · `delete_file` · `diff` · `create_branch` · `commit_and_push` · `discard_changes` | Change that code on a branch and push it |
| `stack_repo_write` | Write a new application into the stack repository itself — one folder per application under `apps/`, with its own Dockerfile — using the token the platform already holds |
| `spec_kit` | Spec-driven development for application components, with a constitution generated from the actual stack. Switched on by the MCP component's `ai_workflow` attribute |

The code tools appear for each application component the MCP server is linked to.

Before recommending application work, the model checks what specifications and tasks are
already in flight, so two sessions do not design the same feature twice. Shared project
state lives in your repositories, not in a client's private memory.

## Scheduled autonomous work

The MCP server can also run **unattended**. Two sub-component types on the MCP server turn
a conversation into a standing job:

| Sub-component | What it is |
|---|---|
| `agent` | A configured AI worker: which model, which tool categories it may use, its budget |
| `ai_task` | A task with a schedule, a prompt, a notification target, and optional chaining to another task |

Tasks run on a cron expression inside the stack, call the same MCP tools a human
conversation would, track token usage and cost per task, and report by webhook or email.
Chained tasks pass their result to the next one. This is how a nightly compliance run, a
weekly dependency review or a continuous drift watch is expressed — as part of the stack,
versioned with it.

| Tool | What it does |
|---|---|
| `dark_factory_status` | Every agent's configuration and every task's state, last run and result |
| `dark_factory_history` | The run history of one task |
| `dark_factory_run_now` | Run a task immediately, skipping its schedule; a chain continues on success |
| `dark_factory_toggle_agent` | Switch an agent on or off at runtime, without a redeploy |
| `dark_factory_cost` | Token usage and estimated cost per task, and in total |

External stacks

Multi-stack
Several stacks, each with its own graph, wired where they meet

A shared platform stack, several product stacks and a central observability stack are separate systems. Each keeps its own graph, lifecycle, history and validation. A cell published by one can be drawn in another, and the links to it generate the cross-stack configuration.

Publishing and copying a cell​

A system is published with the eye icon on its card. Its components are then offered under External systems on the design page of everyone who has a role on it. A published system with a pending catalog change is not offered until it is synchronized.

Once copies exist:

DirectionBehaviour
A copy is added elsewhereThe origin records that another system holds a copy
The origin changesName, type, group, attributes, added sub-components and links are propagated into every copy
The origin loses somethingThe copies lose it too, along with the links that depended on it
A copy is removedThe origin stops listing that system
Name a system before you publish it

Cross-system references are resolved by the system's title. Renaming a system that other designs reference breaks those references without a warning.

What a build does with copies​

When a system that shares cells is built, the build page first opens External & Referenced Components Build Settings:

ListWhat it holdsWhat ticking does
External componentsThe copies on your canvas, taken from other systemsTicking the component also renders it, creating its folder in your repository. Ticking Links imports the links it has in its own system: the components at its other ends are added, named <origin title>_<name>
Referenced componentsFor each of your cells that other systems copied, the components those systems linked to itTicking one renders it, creating its folder in your repository

Ticked or not, all of them are written to stack-metadata.yaml, so your components' templates see them at the other end of their links.

Two marks: external and referenced​

Mark in stack-metadata.yamlMeaningHow templates treat it
is_external: trueThe component lives in another clusterNothing is rendered in its name. A template with cross-stack handling connects to the address in an attribute instead of an in-cluster name
is_referenced: trueA placeholder for another system's componentRendered as a local component, as every other template would render it

A template that has no cross-stack handling for a link treats the copy as local: it uses the copy's namespace and in-cluster service name. That only resolves when both stacks run in the same cluster.

Links that work across stacks​

These are the links whose templates connect to another stack's address, and the attribute that carries it. It is the same list the network policy generator uses (below).

LinkWhere the other stack's address isTypical use
prometheus-prometheusThe remote Prometheus component's remote_host; the master's remote_alertsCentral metrics: every stack sends its metrics by remote write, labelled with its stack name
alloy-lokiThe Alloy component's remote_host (the full push URL) and the Loki api_keyCentral logs: the tenant is the sending stack's name
falco-opensearch, crowdsec-opensearch, trivy-opensearch, opa-opensearch, otel-opensearch, fastmcp-opensearch, external_source_code-opensearchThe link's remote_hostCentral SIEM and search. suricata-opensearch reads remote_host too, but the network policy generator does not open its egress yet
otel-clickhouse_db, grafana-clickhouseThe link's public_hostCentral traces and analytics
Airflow ETL links to and from clickhouse_dbThe link's public_hostData jobs against a central warehouse
kanso-prometheus, kanso-loki, kanso-opensearchThe link's remote_host, when setA work tracker that watches another stack
external_secrets-openbaoThe External Secrets component's secret_store_hostOne secret store for several stacks
argo_cd-argo_cdThe link's cluster_api_serverCentral delivery: one Argo CD deploys other clusters
prometheus-opensearchThe Prometheus component's remote_alertsThe central OpenSearch reads another stack's alerts

Anything not in this list — a database, a bucket, an identity provider, a queue in another stack — renders as a local in-cluster address.

The common shapes​

ShapeOn the graphWhat it generates
Central metricsEach application stack's Prometheus links prometheus-prometheus to the central one, marked prometheus_masterRemote write from every stack, each series labelled with the stack it came from; the central Prometheus accepts samples up to an hour late
Central dashboardsThe central Grafana links to its PrometheusOne dashboard folder per stack whose metrics arrive
Central logsEach stack's Alloy links alloy-loki to the central LokiLogs pushed with the stack name as tenant; dashboards live on the central stack
Central SIEMEach stack's Falco, CrowdSec, Trivy and OPA link to the central OpenSearchOne SIEM with every stack's security events
Central deliveryEach stack's Argo CD links argo_cd-argo_cd to the central oneThe central Argo CD generates Applications per managed cluster, cluster by cluster
Shared servicesA cell of another stack is drawn in your designGenerated through the template's cross-stack handling where it has one; otherwise as an in-cluster address that works only when both stacks share a cluster

Network policies across stacks​

The network policy generator handles the two directions of a cross-stack link differently.

DirectionWhat is generated
Into this stack, through its gatewayA link from another stack's component into a local one, with remote_host pointing at this stack's gateway, opens gateway → target on the port the gateway route to that component type uses. The build log and networkpolicy-manifest.json (cross_stack) list every such rule
Out of this stackA local pod that connects to another stack's address gets egress on that address's port, read from the attribute in the table above. When the address is an IP, only that IP is opened. When it is a host name, the port is opened to any destination, because a network policy cannot match names. The policy annotation stacktic.io/cross-stack-hosts, the build log and the manifest (cross_stack_outbound) name every opened host
A cross-stack link with no addressWarned in the build log and listed under cross_stack_unaddressed in the manifest

A stack without cross-stack links renders exactly what it rendered before. In the strict regulated set (microsegmentation_level: pci_dss_strict), these explicit rules are what keeps cross-stack connections working without a blanket internet egress — see Network policies.

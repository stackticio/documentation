Systems and builds

Work
From a drawing to a repository

A system moves through a small, explicit lifecycle. Every transition is recorded, and every recorded transition carries the diagram it was made from.

The lifecycle​

StateMeaning
CreatedThe system exists, with a default configuration and one environment
SavedThe current diagram is stored. Each save is its own version
BuildingA build is running; logs stream while it does
GeneratedThe build finished and the repository was written
FailedThe build stopped; the logs say where

The actions​

ActionWhat it does
SaveStores the diagram as a new version. Optionally evaluates the catalog's suggestions against it
BuildRenders every component, aggregates the repository, runs the post-generation chain and commits
Save & pushSaves, then regenerates only what the changed attributes can affect
PushThe same incremental path, using work the platform already pre-rendered in the background after your last save
CancelStops a running build between steps, and between components
HistoryEvery version, with a cell-by-cell diff between any two
RollbackLoads an earlier version's diagram back onto the canvas
Pre-rendering makes pushes fast

After an effective save, the platform quietly renders the system's components in the background. When you then push, most of the work is already done. A newer save supersedes a running pre-render at a component boundary, so the result always matches what you last saved.

Validation​

Before a programmatic build, save-push or attribute change is accepted, the whole diagram is checked against the catalog:

unique component and sub-component namesname formatcatalog entry existstype matches the catalogversion matches the cataloggroup matchesexactly the catalog's attributes — none missing, none extraallowed values for select lists and togglesfree text matches the catalog patterna sub-component's parent can own itevery link is one the catalog permits

That is what makes "the AI cannot invent a component type" a property of the system rather than a promise.

Environments​

A system's configuration lists its environments. The base output is shared; each environment gets an overlay with only its differences. Adding an environment is a configuration change, not a new design.

The divergence list​

The generated repository is yours to extend, so the platform has to know what to do when your copy of a file differs from what it would generate.

ChoiceBehaviour
MergeThe default for any file without a stored choice: a three-way merge
OverwriteThe file is brought back to what the platform generates
IgnoreThe platform never touches this file again

Only ignore is remembered — an overwrite makes the file match, and a merge is the default anyway, so neither needs to be stored. On a push, a conflict stops the operation instead of committing conflict markers.

Build logs​

Logs stream while the build runs, and each step reports its own timing, so a slow build can be attributed from the log alone. The build log ends with the exact apply commands for what changed.

Folders and visibility​

Systems live in nested folders, personal or shared. A system can additionally be marked as externally visible, which is what allows other users to pull its cells into their own designs.

<Hero eyebrow="Reference" title="The catalog is the vocabulary">
A component type is not a suggestion. It is the set of things the platform knows how to
generate, wire, secure, validate and operate. Anything outside it is a gap to be named,
never something to improvise around.
</Hero>

<Stats>
  <Stat value="69" label="components you can draw" />
  <Stat value="418" label="link types their templates generate configuration for" />
  <Stat value="60+" label="sub-component types" />
</Stats>

:::note Where these numbers come from
The 69 are the catalog's drawable components (November 2026). The link types are the ones the
templates of those components read, from the platform's generated inventory of its templates. The
sub-component types are counted from the same templates; the count is a floor, not an exact figure.
Templates kept only so that older stacks still generate are not counted. The numbers move as the
catalog grows.
:::

:::note The authoritative list is the catalog itself
Entries are version-pinned, and the catalog states which version is current for each
component. Ask your AI client (`knowledge`) or the platform for the live list rather than
treating any document as the source of truth — including this one.
:::

## Your applications

| Component | What it is for |
|---|---|
| **External source code** | Your own code, built in-cluster from your repository. The centre of most stacks; its `migration_command` runs schema migrations before each new pod starts |
| **Image base** | A pre-built container image you already have |
| **FastAPI** | A scaffolded Python API, when you want the platform to write the starting point |

## Deprecated entries

Some catalog entries exist only so that stacks built on them still generate. They carry a
reduced attribute and link surface and are never offered as a choice for a new design. If
you find yourself looking at one, the answer is the current default for that component.

Detection and response

Watch
Three sensors, one decision point, one SIEM

Network intrusion detection, runtime detection and log-based intrusion prevention are components of the stack. The links between them, and from them to OpenSearch and Prometheus, decide where their events go and what acts on them.

The three sensors​

ComponentRuns asSeesActs
SuricataA DaemonSet: one passive sensor per nodeTraffic on the node's network interface. Pod-to-pod traffic on the same node never crosses the interface; inbound HTTPS shows TLS metadata (SNI, certificates, JA3/JA4) onlyNever blocks. Writes EVE JSON events
FalcoA DaemonSet with an eBPF driverSystem calls, file access and network activity of containers and hostsRaises events at or above falco_priority
CrowdSecA Local API (one replica) and an agent on every nodeThe container logs of linked sources: the gateway's access log, Suricata's eventsRaises alerts; the Local API turns them into decisions that are enforced

They run side by side without conflict: no shared port, kernel hook or file. Suricata captures with AF_PACKET, Falco hooks system calls with eBPF, and the CrowdSec agent reads logs through a read-only host path.

CrowdSec: from a log line to a ban​

On the graphWhat it does
apisix-crowdsecThe agent tails the gateway's access log; a parser turns it into the fields the HTTP scenarios need. The same link registers the gateway as the WAF's bouncer
crowdsec-suricataThe agent tails Suricata's event stream and runs the Suricata scenarios
crowdsec_collectionsThe hub collections the agent installs: parsers and scenarios
crowdsec_simulationOn: scenarios run and alerts are raised, flagged simulated, but no decision is issued. Tune here, then switch it off to enforce
crowdsec_remediation, crowdsec_ban_durationban or captcha, and for how long; per address only
crowdsec_firewall_bouncerA DaemonSet on the host network that pulls the ban decisions every 10 seconds into an nftables set, so a banned address is dropped before it reaches the node's own ports or a pod. Built in the cluster from a pinned upstream release whose checksum is an attribute: a mismatch fails the build
crowdsec_allowlistAddresses that never reach a scenario — put the operators' addresses here. Private addresses never produce a decision
crowdsec_capi_sharingOn: the Local API enrols with CrowdSec's Central API, shares attacker addresses and pulls the community blocklist. Off: nothing leaves the cluster
waf sub-componentsThe web application firewall at the gateway — see Gateway, login and private access

Request-level blocks are the WAF's job; address-level bans are the firewall bouncer's.

Suricata: what to set​

AttributeMeaning
suricata_home_netThe address ranges Suricata treats as yours
suricata_rule_sources, suricata_update_intervalRule sources for suricata-update (Emerging Threats Open by default) and how often they refresh, in hours
suricata_disable_rules, suricata_thresholdsNoise suppression: rules turned off, and thresholds
suricata_eve_typesThe event types written, for example alert and stats
suricata_interfaceThe interface to sniff; auto takes the default-route interface

Where the events go​

LinkDestination
suricata-opensearchA shipper sidecar sends the events to OpenSearch, index suricata-events
falco-opensearchFalcosidekick sends Falco's events to OpenSearch
crowdsec-opensearchThe Local API posts every alert, WAF matches included, to the index crowdsec-alerts
trivy-opensearch, opa-opensearch, apisix-opensearchVulnerability reports, admission violations and gateway logs in the same SIEM
prometheus-crowdsec, prometheus-suricata, prometheus-falcoMetrics and alert rules in Prometheus

Without its link, a sensor keeps its events on the node or in its own pods.

The SIEM​

The OpenSearch component turns each inbound link into a SIEM source. For every linked source it creates the index template, the dashboards, and the alerting monitors where the source has them — Falco, Suricata and CrowdSec — plus a security overview dashboard across all of them, all from a bootstrap Job.

AttributeMeaning
retention_hot_days, retention_warm_days, retention_total_daysThe index lifecycle policy for the SIEM indices: warm after the hot period, deleted after the total

A central SIEM for several stacks is the same links drawn to another stack's OpenSearch, with the link's remote_host — see External stacks.

Alerts and dashboards​

ComponentPrometheus alert rulesGrafana
CrowdSecThe Local API is down; an agent is missing on a node; no log source has matched for 30 minutesThe four official CrowdSec dashboards
SuricataA sensor is missing or not scheduled on a nodeThe Suricata sensor fleet dashboard; Suricata itself exposes no metrics endpoint, so its signatures and flows are read in OpenSearch
FalcoFalco's ServiceMonitor and alert rules, with prometheus-falcoThe Falco and Falcosidekick dashboards

Dashboards are provisioned by the stack's Grafana when its Prometheus has the matching prometheus-<type> link.

From an AI client​

With a fastmcp-opensearch link, the MCP server's SIEM tools query the Falco, Trivy, OPA, APISIX and OpenTelemetry indices. CrowdSec and Suricata events are read in OpenSearch's own dashboards.

the stack. The links between them, and from them to OpenSearch and Prometheus, decide where their
events go and what acts on them.

## The three sensors

| Component | Runs as | Sees | Acts |
|---|---|---|---|
| **Suricata** | A DaemonSet: one passive sensor per node | Traffic on the node's network interface. Pod-to-pod traffic on the same node never crosses the interface; inbound HTTPS shows TLS metadata (SNI, certificates, JA3/JA4) only | Never blocks. Writes EVE JSON events |
| **Falco** | A DaemonSet with an eBPF driver | System calls, file access and network activity of containers and hosts | Raises events at or above `falco_priority` |
| **CrowdSec** | A Local API (one replica) and an agent on every node | The container logs of linked sources: the gateway's access log, Suricata's events | Raises alerts; the Local API turns them into decisions that are enforced |

They run side by side without conflict: no shared port, kernel hook or file. Suricata captures with
AF_PACKET, Falco hooks system calls with eBPF, and the CrowdSec agent reads logs through a read-only
host path.

## CrowdSec: from a log line to a ban

| On the graph | What it does |
|---|---|
| `apisix-crowdsec` | The agent tails the gateway's access log; a parser turns it into the fields the HTTP scenarios need. The same link registers the gateway as the WAF's bouncer |
| `crowdsec-suricata` | The agent tails Suricata's event stream and runs the Suricata scenarios |
| `crowdsec_collections` | The hub collections the agent installs: parsers and scenarios |
| `crowdsec_simulation` | On: scenarios run and alerts are raised, flagged simulated, but no decision is issued. Tune here, then switch it off to enforce |
| `crowdsec_remediation`, `crowdsec_ban_duration` | `ban` or `captcha`, and for how long; per address only |
| `crowdsec_firewall_bouncer` | A DaemonSet on the host network that pulls the ban decisions every 10 seconds into an nftables set, so a banned address is dropped before it reaches the node's own ports or a pod. Built in the cluster from a pinned upstream release whose checksum is an attribute: a mismatch fails the build |
| `crowdsec_allowlist` | Addresses that never reach a scenario — put the operators' addresses here. Private addresses never produce a decision |
| `crowdsec_capi_sharing` | On: the Local API enrols with CrowdSec's Central API, shares attacker addresses and pulls the community blocklist. Off: nothing leaves the cluster |
| `waf` sub-components | The web application firewall at the gateway — see [Gateway, login and private access](/docs/security/edge#web-application-firewall) |

Request-level blocks are the WAF's job; address-level bans are the firewall bouncer's.

## Suricata: what to set

| Attribute | Meaning |
|---|---|
| `suricata_home_net` | The address ranges Suricata treats as yours |
| `suricata_rule_sources`, `suricata_update_interval` | Rule sources for `suricata-update` (Emerging Threats Open by default) and how often they refresh, in hours |
| `suricata_disable_rules`, `suricata_thresholds` | Noise suppression: rules turned off, and thresholds |
| `suricata_eve_types` | The event types written, for example `alert` and `stats` |
| `suricata_interface` | The interface to sniff; `auto` takes the default-route interface |

## Where the events go

| Link | Destination |
|---|---|
| `suricata-opensearch` | A shipper sidecar sends the events to OpenSearch, index `suricata-events` |
| `falco-opensearch` | Falcosidekick sends Falco's events to OpenSearch |
| `crowdsec-opensearch` | The Local API posts every alert, WAF matches included, to the index `crowdsec-alerts` |
| `trivy-opensearch`, `opa-opensearch`, `apisix-opensearch` | Vulnerability reports, admission violations and gateway logs in the same SIEM |
| `prometheus-crowdsec`, `prometheus-suricata`, `prometheus-falco` | Metrics and alert rules in Prometheus |

Without its link, a sensor keeps its events on the node or in its own pods.

## The SIEM

The OpenSearch component turns each inbound link into a SIEM source. For every linked source it
creates the index template, the dashboards, and the alerting monitors where the source has them —
Falco, Suricata and CrowdSec — plus a security overview dashboard across all of them, all from a
bootstrap Job.

| Attribute | Meaning |
|---|---|
| `retention_hot_days`, `retention_warm_days`, `retention_total_days` | The index lifecycle policy for the SIEM indices: warm after the hot period, deleted after the total |

A central SIEM for several stacks is the same links drawn to another stack's OpenSearch, with the
link's `remote_host` — see [External stacks](/docs/platform/external-stacks).

## Alerts and dashboards

| Component | Prometheus alert rules | Grafana |
|---|---|---|
| CrowdSec | The Local API is down; an agent is missing on a node; no log source has matched for 30 minutes | The four official CrowdSec dashboards |
| Suricata | A sensor is missing or not scheduled on a node | The *Suricata sensor fleet* dashboard; Suricata itself exposes no metrics endpoint, so its signatures and flows are read in OpenSearch |
| Falco | Falco's ServiceMonitor and alert rules, with `prometheus-falco` | The Falco and Falcosidekick dashboards |

Dashboards are provisioned by the stack's Grafana when its Prometheus has the matching
`prometheus-<type>` link.

## From an AI client

With a `fastmcp-opensearch` link, the MCP server's SIEM tools query the Falco, Trivy, OPA, APISIX and
OpenTelemetry indices. CrowdSec and Suricata events are read in OpenSearch's own dashboards.

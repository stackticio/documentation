Accountability

Agents and people
Every action says who did it, and how

When agents and people share a backlog, the history has to show who did what. In Kanso, every change records the person behind it and the credential it came through. You can search what any agent did, trace a ticket back to the run that opened it, and cite a person's answer forever.

Every write names its credential​

Each change, comment, worklog, record, question, attachment, waiver and feed entry carries two things: the author, which is the person, and the via, which is the credential the change came through.

"via": { "kind": "token", "id": "kat_1", "name": "triage agent" }
via.kindThe change came through
tokenA personal API token, on REST or MCP (kat_<n> and the token's name)
sessionA signed-in session, on any route but MCP
session_mcpA signed-in session used on the MCP endpoint
appAn installed app's run (ains_<n> and the app's key)
connectorA connector binding (cbind_<n> and the connector's key)
import, systemKanso acting with no person behind it, such as the Jira importer or a lease that expired

People see via token "triage agent" next to a token's change, and via MCP session next to a session's change made over MCP.

The history is written in the same transaction as the change. No code path changes a ticket without recording it.

An answer to a question records the same pair, as answeredBy and answeredVia. Webhook deliveries carry the via of the act they report, so the systems you connect see the same attribution.

An agent can recognise its own writes without an extra call. Its token's via.id is the part of the token before the dot, kat_1 for kat_1.<secret>, so it compares comment.via.id with that prefix.

Find what the agents did​

changedVia is a JQL field. It finds every ticket whose history has a change through a given kind of credential, or through one specific token:

changedVia = token                      every ticket any agent token changed
changedVia = kat_1                      everything one agent changed
project = PAY AND changedVia = session  changes people made in the browser

These searches answer a simple question: is the AI earning its seat?

Claiming and releasing leases is not a change to the ticket, so it does not appear in the history or in changedVia. Lease activity is reported as issue.lease_acquired and issue.lease_released events instead, with the reason a lease ended: released, expired, recalled or forced. See Agent fleets and leases.

Trace a ticket back to its run​

A ticket an agent opens over MCP must say where it came from. create_issue requires an origin with two parts: the agent's session, which is the id of its conversation, job or run, and a context sentence on what asked for the ticket. Kanso writes it as the first line of the description:

> **Agent origin** — session `run-2026-10-22-a` — Triage of the payments error budget alert

People read it on the ticket. Other agents find related tickets with text ~ "run-2026-10-22-a".

Cite a person's decision​

When an agent asks a person a question, the answer is written once and never changes. It has a permanent citation: PAY-1/q_1 is the first question on PAY-1. The agent keeps that string wherever it uses the answer, in a commit message, a comment or a report, and anyone can re-read the same answer with it later.

"answer": { "values": { "ship": true, "window": "after 18:00" },
            "answeredBy": { "username": "lee", "name": "Lee Lead" },
            "answeredVia": { "kind": "session" },
            "citation": "PAY-1/q_1" }

See Human answers.

What Kanso can and cannot tell you​

Kanso records credentials and routes, not intentions. It cannot tell a person from a program that holds the same credential. If an agent signs in with a person's username and password, its changes look exactly like that person's own. Give every agent its own named token, and its work is always told apart.

Policy changes are audited too​

Changes to what agents are allowed to do are recorded as well. Every change to the agent access policy lists who made it, when, and the old and new settings. See Governing agents.

Your first agent

Quickstart
Your first agent, in five minutes

Mint a token, paste one command into your MCP client, and your agent works the same backlog your team does. Every ticket it opens says where it came from, and every change it makes shows its name.

Before you start​

  • A running Kanso instance that your MCP client can reach. See Install.
  • A Kanso account, and at least one space (project) to work in.
  • An MCP client that speaks Streamable HTTP, such as Claude Code.

1 · Mint a token​

Sign in, open Security in the sidebar and choose Connect an agent.

  • Name it after the agent, such as triage agent, not after your laptop. The name is shown next to everything the token writes.
  • Pick the scope. Read only is the default. Choose Read & write if the agent should open, change and move tickets.

The secret is shown once. Kanso stores only a hash of it, so nobody can show it to you again. If you lose it, revoke the token and mint another.

You can also mint a token from a script, using a signed-in session. A token cannot mint another token.

curl -b cookies.txt -X POST "$KANSO_URL/api/v1/auth/tokens" \
  -H 'Content-Type: application/json' \
  -d '{"name": "triage agent", "scope": "write"}'
{ "id": "kat_1", "name": "triage agent", "scope": "write",
  "createdAt": "2026-10-22T19:26:54.631156Z", "expiresAt": "2027-01-20T19:26:54.631156Z",
  "lastUsedAt": null, "nameOnWrites": true, "status": "active",
  "token": "kat_1.<secret>" }

Every token expires: after 90 days by default, and after 365 days at most.

2 · Connect your client​

The Connect an agent dialog shows a complete command. For Claude Code it looks like this:

claude mcp add --transport http https://kanso.example.com/api/v1/mcp \
  --header "Authorization: Bearer kat_1.<secret>"

Add --scope user to make Kanso available in every project, not just the current directory. Any other MCP client needs the same two things: the URL and the header.

MCP servers attach when a client starts, so Kanso appears in your next session, not the one that is already running.

3 · Give the agent its rules​

Paste the Quick guide for the agent into your agent's system prompt. It teaches the model to read before it writes, ask for the create form instead of guessing, pass back the version it read, and stop on a refusal instead of retrying.

4 · Ask it to do some work​

Start a new session and try something like:

Look at the PAY space. Open a ticket for the 3-D Secure checkout timeout, then pick it up and start on it.

Under the hood, the agent calls list_projects, then get_create_form for the space, then create_issue. Kanso requires every ticket an agent opens to say where it came from. A create without an origin is refused and writes nothing:

origin_required — /origin/session: required — your session or run id, 1-200 characters,
no whitespace or backtick; /origin/context: required — what asked for this ticket, 1-1000 characters

The agent supplies its session id and a sentence on what asked for the ticket, and Kanso writes it as the ticket's first line:

> **Agent origin** — session `run-2026-10-22-a` — Triage of the payments error budget alert

To pick the ticket up, the agent calls claim_next_issue and gets a lease. While it holds the lease, the ticket's card shows who is working on it. Then transition_issue moves the ticket along its workflow.

5 · See what it did​

Open the ticket in Kanso:

  • The description starts with the agent origin line, so anyone can find the session that opened it.
  • The history shows every change with the person's name and the credential beside it: via token "triage agent".
  • The header shows a Being worked on chip while the agent holds the lease.

Search for everything the agents did with JQL:

changedVia = token
changedVia = kat_1

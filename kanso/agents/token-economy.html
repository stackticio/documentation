Token economy

簡 素 · Agents · cost
Spend fewer tokens. Know what each ticket cost.

An agent pays for everything it reads: the tool list, the ticket, the waiting. Kanso keeps all three small, and lets the agent's harness report what each ticket actually cost, so a person can set a budget the agents respect.

What already saves tokens​

shipped · 0.77
  • One call reads a whole ticket. get_issue returns the ticket with the transitions available right now, its links, its first 50 children and its newest 50 comments, in one call. An agent does not fan out into five reads.
  • Search returns summaries, a page at a time. search_issues returns summary rows, maxResults from 1 to 100 (default 25), and a nextPageToken until isLast.
  • Waiting is one held request, not a poll loop. await_question and await_issue hold for up to 60 seconds and answer within a second of the change. Calling get_question every few seconds instead burns a model turn each time.
  • Fewer tools, smaller context. The client loads the whole tool list into the model's context. A read-only token sees only the read tools, and the agent access policy can hide the optional groups. The Strict preset hides all of them.

Next release: four more​

next release

The worker tool set​

Connect with ?profile=worker on the MCP URL, and the agent gets the 17 tools it needs to work tickets: search, read, claim, update, transition, comment, file, link, ask and wait. The Connect an agent dialog offers it as the default Tool set.

claude mcp add --transport http "https://kanso.example.com/api/v1/mcp?profile=worker" \
  --header "Authorization: Bearer kat_1.<secret>"

A profile only narrows what the token could already do. It never grants anything. A tool outside the profile is refused with a message that says how to get it:

mcp_tool_not_in_profile: the list_projects tool is not in the MCP tool profile "worker" this
connection asked for (?profile=worker); connect without ?profile, or with ?profile=full …

Children as summaries​

get_issue now returns each child as a summary: key, summary, type and status, plus assignee, parent, labels, priority, resolution and lease when they are set. There is nothing to configure. An epic with 25 children cost 35,102 characters of children before, and 5,835 now.

{ "key": "OPS-4", "summary": "Checkout follow-up 1: harden the payment client retry path",
  "type": "Task", "status": "To Do", "statusCategory": "todo",
  "parent": "OPS-3", "priority": "Medium", "labels": ["checkout", "reliability"] }

Ask once: search past answers​

Before an agent asks a person, it can check whether someone already answered. search_answers searches answered questions by text, space, ticket, who asked, who answered, state and date, and returns each answer with its citation:

search_answers  text: "roll back"   →   OPS-1/q_1 · Lee Lead · { "rollback": true }

Kanso's team measured the old way of finding a past decision at 126 calls and 90,199 characters for a single lookup. It is now one call.

Wake instead of wait​

An agent that asks a question can name a wake target (wake: "<target>" on ask_question) and exit instead of holding. When the person answers, Kanso rings the target, an app such as wake-http that starts your runner, and a new run of your agent continues from the ticket. A site admin registers the targets on the Wake targets screen.

Know what each ticket cost​

next release

Kanso does not count tokens. Only the agent's harness can. The harness reports what a run spent on a ticket, and Kanso keeps it as data next to the work:

curl -X POST "$KANSO_URL/api/v1/issues/OPS-2/usage" \
  -H "Authorization: Bearer $KANSO_TOKEN" -H 'Idempotency-Key: run-1' \
  -H 'Content-Type: application/json' \
  -d '{"inputTokens": 182000, "outputTokens": 9400,
       "cacheReadTokens": 150000, "cacheWriteTokens": 21000,
       "costMicros": 812000, "model": "claude-sonnet", "source": "claude-code",
       "harnessSession": "inc-2026-10-22-checkout"}'

The ticket now shows Agent usage: 362,400 tokens and $0.81 across one run. Usage reported after a ticket went back to a status it had left counts as rework. The Usage report, GET /api/v1/reports/usage, groups spend by ticket, parent, label, model, session, person, credential, source, status or day, over up to 92 days.

A budget the agents respect​

A person sets a token budget, a cost budget, or both, on a ticket. Only a signed-in person can: a token is refused with session_required. Once reported usage reaches the budget, agents stop picking the ticket up:

budget_exceeded: the agent budget of OPS-2 is spent (set by sam) — stop, release the issue
and ask sam to raise it — /agentBudget/tokens: used 362400 of 150000

claim_next_issue skips tickets over budget and counts them in overBudget. The budget never blocks comments, questions, transitions or further usage reports, and it never blocks a person. It is a brake for well-behaved agents, not a security control. The access policy and the token are the security controls.

In development: the wait strategy​

in development

The next step lets a space choose how an agent waits for a person: hold briefly, resume the same conversation when the answer comes, or start fresh from the ticket's handoff. Kanso's design compares the three with plain arithmetic. These are estimates, not measurements. They assume a 100,000-token conversation, an answer three hours later, published cache ratios (cached read 0.1×, cache write 1.25×, a 5-minute cache) and a 15,000-token fresh read:

Way of waitingArithmeticInput-token equivalents
Hold, once a minute for three hours180 × 100,000 × 0.11,800,000
Resume the conversation100,000 × 1.25125,000
Start fresh from the handoff15,000 × 1.2518,750

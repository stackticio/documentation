Operator tickets

簡 素 · Operations
From an alert to an agent on the case.

When production breaks, your alerting already knows. Kanso turns each problem into exactly one ticket. An agent picks it up and investigates, a person makes the calls that need a person, and every step lands on the ticket.

kanso
next release · signals, agent sessions, handoffin development · routing by ops policyBuilt, and run end to end on the current build. These ship in the release after 0.77.0.
朱

Your alerting says what is wrong. The space decides what becomes a ticket. The agent does the investigation. A person makes the calls. Kanso keeps all of it on one record.

Connect your alerting​

Kanso takes problems in as signals: things a monitored system reports as wrong right now, each with the source's own fingerprint. Two connectors for this come in the catalog:

Catalog entryForConfigure
alertmanagerPrometheus AlertmanagerA receiver pointed at the instance's URL, with send_resolved: true
signalsAny monitor, log pipeline or scriptPOST {"source": …, "signals": [{fingerprint, title, status?, severity?, url?, data?}]}

Kanso does not receive OpenTelemetry (OTLP) itself. If your telemetry, OpenTelemetry included, drives alerts in Alertmanager or in any system that can send a webhook, those alerts become signals. A script can send the signals shape directly.

Install the connector

In Connectors, install Prometheus Alertmanager from the catalog.

Bind it to a space

Binding creates an instance in the space and returns its ingest URL and its secret, for example /api/v1/ingest/cbind_1.

Point Alertmanager at it

Add a receiver that sends to that URL with the secret:

receivers:
  - name: kanso
    webhook_configs:
      - url: https://kanso.example.com/api/v1/ingest/cbind_1
        send_resolved: true
        http_config:
          authorization:
            credentials: <the instance secret>
Let the space open tickets

Tickets are off by default. On the instance, choose signals and turn tickets on. That needs manage_connectors and create_issue in the space. You can also pick the issue type, the link type for recurrences, and the storm cap.

The same settings over the API:

curl -X PUT "$KANSO_URL/api/v1/connector-bindings/cbind_1/signal-settings" \
  -b cookies.txt -H 'If-Match: 1' -H 'Content-Type: application/json' \
  -d '{"tickets": true, "issueType": null, "linkType": "lt_4",
       "storm": {"tickets": 20, "windowMinutes": 10}}'

One problem, one ticket​

Each delivery reports what it did:

{ "delivery": "del_1",
  "signals": { "seen": 1, "opened": ["OPS-1"], "cleared": 0, "stormed": 0 } }
WhenWhat Kanso does
A new problem firesOpens one ticket, attributed to the connector, titled from the alert: CheckoutErrorRate on checkout-7f9c. It carries a signal record with status firing.
The same problem fires againUpdates the record. No second ticket opens (opened: []).
The problem resolvesMarks the record cleared. The ticket is not changed. Nothing closes, comments on or moves it. Closing it is a decision.
It fires again after the ticket is doneOpens a new ticket, linked to the old one, that says Fired again after OPS-1 was done.
Too many problems at onceAbove the storm cap (20 new tickets per 10 minutes by default), the rest go onto one storm ticket.

The ticket starts with where the problem came from:

> **Signal** from connector `alertmanager` · fingerprint `9c1e4f7a2b`

Source: http://prometheus.example/graph?g0.expr=job%3Acheckout_5xx

The alert's labels, annotations and start time stay on the signal. Find every open problem with JQL:

record = "signal:firing"

An agent takes the case​

Claim the problem

The agent claims from the open problems, highest priority first. It sends its own run id in the Kanso-Session header, so its work is grouped as one session.

claim_next_issue  jql: record = "signal:firing" ORDER BY priority DESC
Investigate on the ticket

It reads the ticket and the source link, and posts what it finds as comments: 5xx started 20:09, right after deploy checkout v2.14. Rollback candidate: v2.13.

Ask for the call that needs a person

It asks a typed question on the ticket, Roll checkout back to v2.13?, and waits. The lead answers yes. The answer comes back as data, with a citation: OPS-1/q_1.

Hand off, or finish

When it stops, it releases the ticket and leaves a handoff in the same call: where the work stands, what to do next, what blocks it, and where the work is. The next session, agent or person, starts from there.

"handoff": {
  "state": "Same 5xx pattern as OPS-1; the rollback did not hold.",
  "next":  "Check the payment-provider timeout added in v2.14.",
  "where": "checkout service, payment client"
}
in developmentRouting by ops policy: a space policy that decides what a signal is worth, how urgent it is, and which queue takes it, as a queue:<name> label. Agents then claim with labels = "queue:…". Built on its own branch and not yet reviewed.

People stay in control​

Every agent run is a session you can see. The Agent sessions page shows each one: whose it is, which token it uses, what it holds, which person it is waiting on, and how long it has been quiet.

{ "id": "as_1", "externalId": "inc-2026-10-22-checkout", "state": "active",
  "credential": { "kind": "token", "id": "kat_1", "name": "oncall agent" },
  "leases":     [{ "issue": "OPS-1", "expiresAt": "2026-10-22T20:36:59Z" }],
  "waitingOn":  [{ "question": "OPS-1/q_1", "assignee": { "name": "Lee Lead" } }] }

You can stop an agent without killing anything:

ActionWhoEffect
Pause a sessionThe token's owner, a site admin, or anyone with pause_agent_sessions in a space where the session is workingIts next work write is refused
Pause all agentsA site adminEvery agent's work writes are refused. People and apps are not affected.
ResumeThe owner or a site admin, signed in. Never a token.Work continues

A pause stops the work but keeps the conversation open. The agent is told exactly that:

session_paused: this agent session (as_1) is paused: it may still read, search, comment,
ask, answer and release its leases, but this operation is refused — its owner or a site
admin can resume it on the Agent sessions page

A paused agent can still leave a handoff and report its usage, so nothing it already did is lost. A pause sticks: if the agent comes back with the same run id, it is still paused.

The honest limits​

  • Kanso does not run agents. It never starts, steers or kills an agent process. It is the record and the doorbell: it opens the ticket, records the work, asks the person and refuses a paused session's next write. Your agents pull the work.
  • No live attach. You see a session's state and its writes, not its screen. To pick up where an agent left off, read its handoff and its comments.
  • One delivery holds up to 500 problems, and an instance tracks up to 1,000 firing ones. Beyond that a delivery is refused with too_many_signals. A delivery is all or nothing.
  • Kanso does not close tickets when a problem clears. To make Done wait until the signal has cleared, put a requirement on the workflow for a signal record with status cleared.

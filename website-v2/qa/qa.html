What do I get from Stacktic that I don't have today?

One model, everything downstream

Your stack stops being a pile of files and becomes one model — components, sub-components, attributes and typed links. Change one thing and everything that depends on it is regenerated, revalidated and re-documented.

  • Automated, auditable config you can review, diff and trust — not YAML nobody remembers writing.
  • Ideas to production in hours, not months.
  • LiveView validation — deep checks into databases and APIs, generated tests and health probes.
  • The guardrails most teams skip: network-policy micro-segmentation, multi-layer RBAC, secret wiring.
  • A CISO-ready posture per stack, with remediation guidance and evidence.
  • Stack version control — save, duplicate to staging, modify, roll back, share.
  • Versioning that survives drift: automations keep working as schemas and dependencies move underneath.
  • Auto-docs — runbooks, diagrams and ops notes generated from the stack itself.
  • A machine-readable surface AI can safely drive.

02

Is Stacktic a SaaS platform — or a framework?

Platform engineering, delivered both ways

Both, and that's the point. Underneath, Stacktic is an automation framework: a metadata model of your stack layers and the logic that compiles their relationships into real code. On top, it is platform engineering as SaaS.

The AI drives almost the entire platform — through the API, not around it. So what is the SaaS for? It is where the humans belong. It's where you get the evidence, where you get the insight, and where you take the manual actions you deliberately choose to keep in your own hands.

Neither half needs the other's permission: the framework runs the automation, the SaaS makes it accountable.

03

How can Stacktic produce compliance evidence — and automate compliance itself?

Evidence is read, never written

Stacktic reads the metadata of every stack layer. From there it can enter any layer, pull the configuration that is actually running in production, validate it against what the stack declares, map the result onto the control it satisfies, and present it as evidence.

The AI does not decide what is compliant. It goes through our API and our metadata, and that path is deliberately limited: it can only return truth derived from code and live state. No opinion. No generated prose standing in for a fact. If it can't be read from the stack, it doesn't appear in the report.

AI already writes my application code. Why do I need Stacktic?

The code is one layer

AI is extraordinarily good at the layer it can see: your service. But production is not a service — it's the stack around it, and the relationships between every part of it.

That's why a feature can be written in an afternoon and still be months from running: the gap isn't code, it's everything code depends on. Stacktic makes those layers, and their links, something a machine can generate, validate, operate and prove.

AI writes the app. Stacktic gives the app somewhere real to live.

07

Can Stacktic automate outside the Kubernetes ecosystem?

Metadata-driven, not cluster-bound

Yes. Stacktic is metadata-driven. A managed database, an external service, a cloud resource or a SaaS endpoint is modelled exactly like anything else — same attributes, same typed links, same generated config on both ends of the link.

The automation reaches them through integrations such as Crossplane, Terraform and cloud APIs. The stack model doesn't care where a component physically lives; it cares what it is linked to.

One model, four kinds of targetthe link is what matters
A link to an external database generates the same things a link to an in-cluster one does: connection config, credentials, network permission and monitoring — on both sides.

Is Stacktic only for deployment, or also for operations?

Day 0 through Day 2

Both — and Day 2 is the harder half. Day 0 gets you provisioned, configured and guarded. Day 1 and Day 2 are where a stack is validated, versioned, migrated, watched and kept safe under load.

Because operations run from the same model that generated the stack, an operational change is not a separate artefact to keep in sync — it's the same model, moving. That is also what lets autonomous agents run on a schedule in monitor or act mode without inventing state of their own.

I'm not comfortable letting AI fully automate my configuration. How much control do I keep?

All of it, by construction

You stay in control. Work in a build branch, read the diff, approve the PR. Best practice and security standards ship by default — and you can modify, extend or ignore any automation.

The AI is constrained on purpose: it acts through the API, its output is validated against the model, and everything it does leaves a reviewable trail. It proposes; the diff is the contract; you merge.

How do I see exactly what Stacktic automates?

360° transparency

Every component carries an info panel and a config preview — the actual files we will generate, before we generate them. Changes arrive as pull requests with diffs. The generated repository ships documentation describing its configuration and its operations.

Which means the answer to "what did it do?" is never a story someone tells you afterwards. It's four artefacts you can open: what it will do, what it did, what is running, and what it proves.
